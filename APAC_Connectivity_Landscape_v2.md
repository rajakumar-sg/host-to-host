## 2. Executive summary

1. **Rails have converged.** All 11 banks in scope publish at least two of three rails: batch file H2H (SFTP/AS2 plus PGP), APIs, and SWIFT (FileAct/SCORE). Quality, onboarding speed and transparency are now the differences.
2. **Differentiation has moved up the stack.** The contest is no longer "do you have H2H" but:
   - absorbing client file-format variance (SC Universal Adaptor, ANZ Fileactive translation, UOB transformation layer);
   - ERP-native adaptors and templates (Citi, J.P. Morgan, HSBC);
   - network membership (SAP MBC: Standard Chartered, Citi, Mizuho in June 2026);
   - approval hand-off from H2H into online banking (UOB, ANZ, SC);
   - regional "one bank" platforms (MUFG Unity April 2026, UOB RFTS across 7 markets, ANZ Fileactive across 7 APAC markets, HSBC Connect).
3. **No bank publishes an end-to-end H2H architecture diagram.** The best public artifacts are the UOB RFTS capability deck, the ANZ Fileactive help centre, the MUFG GPH Swift MyStandards guide, J.P. Morgan's H2H and ERP-adapter pages, CBA's SFTP upgrade page and SC's ISO 20022 H2H/API guideline.
4. **Nobody documents a bank-initiated connection into client ERPs through integration-platform connectors.** The pattern is client-initiated (files or API calls to the bank), or a bank-supplied template/adaptor that runs inside the client's ERP, or a network such as SAP MBC in the middle.
5. **Time-sensitive item:** the ISO 20022 CBPR+ structured/hybrid address change (November 2026) affects H2H file and API submissions (OCBC, SC, MUFG and J.P. Morgan all published notices). J.P. Morgan's page also carries an update saying Swift postponed part of the November release (text truncated in my source). Verify the current enforcement scope and date before relying on it.
6. **Protocol transparency varies.** HSBC, Citi, J.P. Morgan, UOB, ANZ and CBA publish transport-protocol detail. DBS shows it only through a customer story. OCBC, Standard Chartered, MUFG and Mizuho publish none on the pages found.

## 5. Cross-bank reference architecture (my synthesis)

```
Client ERP / TMS
 ├─ (1) Batch file: SFTP / AS2 / FTPS + PGP (encrypt + sign)
 │       -> Bank MFT / file gateway (per-client IN/OUT folders, SSH key, IP allow-list)
 ├─ (2) API: HTTPS REST/JSON + OAuth2/JWT or mTLS (+ PGP payload at DBS)
 │       -> Bank API gateway
 ├─ (3) SWIFT FileAct / FIN / SCORE -> SWIFTNet -> Bank
 └─ (4) Network or aggregator: SAP MBC / FinLync / TMS hub -> Bank tenant or API

Bank side (typical, partly inferred)
 File gateway -> client/partner recognition -> format translation + validation
   -> [optional approval hand-off to online banking: UOB, ANZ Hybrid, SC online release]
   -> payment engine / clearing
   -> acknowledgements (L1-L4 at UOB, pain.002, return status files at ANZ) + statements (camt.052/053, MT940)
   -> back to client over the same rail
```

**Patterns and their meaning (my view)**

| Pattern | Who does it | So what |
|---|---|---|
| Three-rail offer (file, API, SWIFT) | All | Table stakes; the debate is quality and onboarding speed |
| Bank-side format translation | SC Universal Adaptor, ANZ Fileactive, UOB DMP | Reduces per-client mapping effort and rejects; strongest lever for onboarding speed |
| ERP-native templates and adaptors | Citi (SAP DMEE), J.P. Morgan (EBS, D365, SAP), HSBC (SAP) | Shifts mapping work into the client's ERP using standard features |
| Approval hand-off | UOB BIBPlus, ANZ Hybrid, SC online release | Needed for payroll and treasury control |
| Explicit acknowledgement model | UOB L1-L4, ANZ return status files | Gives clients SLAs for reconciliation |
| Network membership | SC, Citi, Mizuho on SAP MBC | Distribution channel into SAP clients; standard formats lower switching cost |
| Regional one-bank platforms | MUFG Unity, UOB RFTS, ANZ Fileactive, HSBC Connect | Multi-country corporates want one H2H contract |
| API portals and sandboxes | HSBC, JPM, UOB, ANZ, SC, Citi | Self-service testing is now expected |
| CBPR+ structured-address readiness | OCBC, SC, MUFG, JPM notices | Affects both file and API rails from November 2026 |

## 6. Design considerations for building the capability (my view)

1. **Decide what to publish:** transport protocols, formats, acknowledgement model and onboarding timeline. UOB, ANZ and CBA show the level of detail clients can reference.
2. **SAP MBC:** request the member-bank onboarding pack (bank tenant, API specification, connection template) and use the Help Portal "Member Banks" page for the authoritative member list.
3. **ERP-side template:** a SAP DMEE template for the bank's pain.001 specification follows the Citi pattern and also feeds MBC mapping.
4. **Translation layer:** decide whether it lives in the MFT/integration layer or is a client self-service feature (SC Universal Adaptor, ANZ Fileactive).
5. **Control hand-off:** decide whether H2H files can route into online-banking approval for payroll and treasury payments.
6. **CBPR+ readiness:** confirm the file and API rails for the November 2026 address change.
7. **Close evidence gaps:** DBS, OCBC, MUFG and Mizuho technical details through relationship managers, peer contacts and Swift MyStandards.
